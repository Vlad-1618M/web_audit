What this report is (and is not)

This document is a passive, external hygiene snapshot of your public website — the same kind of signals a visitor, search engine, or opportunistic attacker could observe without logging in. It is written for owners, managers, and non-developers first; technical evidence lives in the tab.

How to read this report

  • Security dashboard — high-level scores (Hygiene, Exposure) and where the scan focused attention. Hygiene covers configuration and hardening; Exposure covers sensitive paths and leaks.
  • Executive summary — plain-language verdict, priority timeline, and “fix first” items you can forward to your team.
  • Finding status chips — counts by severity. Critical and High action usually need a developer soon; Verify means “confirm in your hosting panel or with your vendor.”
  • Site discovery — URLs and assets catalogued from the homepage and sitemap. Probe rows are deliberate security checks (e.g. /.env); Site rows are normal public pages.
  • Technical details — evidence tables, DNS/TLS/certificate cards, headers, cookies, and extension versions for engineers.

What this report is

  • A repeatable outside-in check you can run after deployments, DNS changes, or certificate renewals.
  • A way to catch obvious misconfigurations — missing security headers, exposed admin paths, weak TLS, email authentication gaps (SPF/DMARC), and outdated plugins when detectable from the outside.
  • A conversation starter between owners and developers: what is urgent vs. what can wait.
  • Free and local — scans run on your machine; no account or cloud upload is required for the audit itself.

What this report is not

  • Not a penetration test. We do not attempt to exploit vulnerabilities, bypass authentication, or chain attacks.
  • Not authenticated testing. We cannot see member areas, checkout flows, or admin consoles that require a login.
  • Not a CDN/WAF replacement. Edge providers (Cloudflare, Fastly, AWS CloudFront, etc.) may block or rewrite what we see; always review their dashboards too.
  • Not compliance certification. Passing this scan does not mean PCI, HIPAA, SOC 2, or ISO approval.
  • Not a guarantee. A clean report today does not prevent issues tomorrow — configuration drift and new releases happen continuously.

Web Audit vs. deeper security tooling

Web Audit Pro is intentionally scoped: fast, readable, and safe for routine owner checks. Many mature open-source and commercial tools go further because they use active probing, authenticated sessions, larger vulnerability databases, or dedicated research teams.

This tool (Web Audit Pro)

Strengths

  • Plain-language owner report
  • Passive / low-disruption external view
  • Runs locally; good for quick regression checks
  • Framework-aware plugin/extension hints

Limits

  • No logged-in or multi-step user flows
  • Limited JavaScript / SPA depth (unless extended)
  • Cannot see internal CDN/WAF rule sets
  • Not a substitute for expert manual review
Stronger open-source & community tools

Why they are more advanced

  • OWASP ZAP — full DAST scanner with spidering, active tests, and authenticated scan profiles.
  • Nuclei — thousands of community templates for known CVEs and misconfigurations.
  • Nikto — deep web-server and CGI checks beyond passive headers.
  • Greenbone / OpenVAS — broad network and service vulnerability management.
  • testssl.sh — exhaustive TLS/cipher analysis.
  • WPScan — WordPress-specific vulnerability intelligence (when applicable).

Trade-offs

  • Steeper learning curve; often aimed at security engineers
  • Active scans can trigger WAF alerts or rate limits if misconfigured
  • More false positives — needs skilled triage
  • Some features require paid tiers or separate infrastructure

Suggestions for your developer or QA team

  • Fix Critical and High action items first; schedule Verify items with your host or CDN vendor.
  • Re-run this audit after each production deploy and compare saved audit_run.json files (webaudit diff).
  • Add header/TLS checks to CI (e.g. curl smoke tests or Mozilla Observatory in pipeline).
  • Schedule periodic authenticated scans (ZAP, Burp Suite Community) on staging before major releases.
  • Keep plugins, themes, and server packages on a documented update cadence; remove unused extensions.
  • Review CDN/WAF, certificate, and DNS dashboards — many findings here are confirmed or dismissed faster with vendor logs.

Permission: Run scans only on sites you own or have explicit authorization to test. If you need formal assurance for investors, insurers, or regulators, engage a qualified penetration testing firm in addition to routine automated hygiene checks.
